# アプリ仕様書 — idea-to-action

## コンセプト

「やりたいこと」を*着手*しやすくするアプリ。

TaskChute の思想（完了より着手を重視する）をベースに、アイデア出しからプロジェクト管理、スケジューリング、振り返りまでを一貫してサポートする。

---

## コアフロー

```
Inbox（雑なアイデアを投げ込む）
  └─ AI コーチングで深掘り
       └─ プロジェクト化
            └─ タスクに噛み砕く
                 └─ タイムラインにスケジュール
                      └─ 通知 → 着手
                           └─ 一日の終わりにレビュー
                                └─ 翌日のスケジュールへ
```

---

## 各フェーズの仕様

### 1. Inbox

- ふわっとしたアイデア・やりたいこと・気になることを雑に投げ込む場所
- テキスト入力のみ。整理は後回しでよい
- アイデアはコーチング開始時に参照される

### 2. AI コーチング

- Inbox のアイデアを起点に、チャット形式でやりとりする
- 目的は「ふわっとした目的を具体的なプロジェクトに落とし込む」こと
- コーチング中の主な問いかけ例：
  - 「何を達成したら成功と言えますか？」
  - 「いつ頃までに？」
  - 「障壁になりそうなことは？」
- 途中で切り上げてもよい（その時点でプロジェクト化できる）

### 3. InboxEntry のライフサイクル

```
active → archived（コーチングでプロジェクト化されたタイミング）
```

- アーカイブ済みエントリはプロジェクトへのリンクを持つ
- 通常の一覧には表示されないが、参照・復元は可能

### 4. タスクのライフサイクル

```
pending → scheduled → started → done
                              └→ skipped → (翌日へ繰り越し候補)
```

- `pending`：作成済み・未スケジュール
- `scheduled`：タイムラインに時刻が割り当てられた
- `started`：着手済み（着手通知に応答、またはユーザーが手動でマーク）
- `done`：完了
- `skipped`：その日に着手しなかった。レビュー時に翌日への繰り越し候補として表示される

### 5. プロジェクト

- コーチングを経て作られた、目標と期限を持つ単位
- 構成要素：
  - タイトル
  - 目的・ゴール（AI との対話から自動生成）
  - 期限（任意）
  - ステータス（アクティブ / 完了 / 保留）
- プロジェクトは複数のタスクを持つ

### 6. タスク

- プロジェクトを「今日・今週できる具体的な行動」に噛み砕いたもの
- ルーティン（毎朝ランニングなど繰り返しのタスク）も管理対象
- 構成要素：
  - タイトル
  - 見積もり時間
  - ステータス（pending / scheduled / started / done / skipped）
  - 所属プロジェクト（ルーティンは独立してもよい）
  - 繰り返し設定（ルーティン用）

### 7. スケジューリング

- タスクをタイムラインに割り当てる
- **ライフプリセット**：ユーザーがあらかじめ生活リズムを登録しておく
  - 例：起床 7:00 / 集中タイム 9:00〜12:00 / 昼休み 12:00〜13:00 / 就寝 23:00
  - AI はこのプリセットとユーザーの傾向・好みを考慮して時間枠を提案する
- **操作方法**：AI 提案を受け入れる、またはユーザーが手動でドラッグして変更
- **将来対応**：Google Calendar / CalDAV との連携

### 8. 通知と着手

- スケジュールされた時刻にプッシュ通知
- 通知の目的は「着手させること」。完了を要求しない
- タスクを開いて「着手した」とマークするだけでOK

### 9. 一日の終わりのレビュー

- **全体負担感**（3 択）
  - 「きつかった」/ 「ちょうどよかった」/ 「余裕だった」
- **タスクごとの振り返り**（スワイプ / タップで素早く回答）
  - 着手できたか：はい / いいえ
  - 目標は達成できたか：はい / いいえ / 一部
- レビュー結果は翌日のスケジューリング提案に反映される
  - 「きつかった」が続く → AI がタスク量を減らすよう提案
  - 未着手タスク → 翌日に自動的に繰り越し候補として表示

## アーキテクチャ方針

TaskWarrior を参考に、**コアロジックを UI から完全に切り離す**設計を採用する。

### 基本構造

```
┌─────────────────────────────────────────┐
│  フロントエンド層（UI）                    │
│  Android アプリ / CLI / 将来の Web UI など  │
└──────────────┬──────────────────────────┘
               │ 呼び出す
┌──────────────▼──────────────────────────┐
│  コア層（pure Kotlin）                    │
│  データモデル / ビジネスロジック             │
│  ストレージインターフェース                  │
└──────────────┬──────────────────────────┘
               │ 実装する
┌──────────────▼──────────────────────────┐
│  データ層                                 │
│  ローカルストレージ（SQLite / JSON）         │
│  将来：CalDAV・外部 API 連携               │
└─────────────────────────────────────────┘
```

### コア層の原則

- Android に依存しない pure Kotlin で書く（`android.*` の import を持ち込まない）
- データモデル（`InboxEntry`, `Project`, `Task` など）はここで定義する
- ビジネスロジック（スケジューリング計算、レビュー集計など）もここに置く
- ストレージはインターフェースとして定義し、実装は各フロントエンドに委ねる

### データ形式

TaskWarrior に着想を得た方針。TaskWarrior はすべてのタスクを `~/.task/` 以下の JSON ファイルとして保持し、DB を使わずファイルが唯一の真実として機能する。本アプリはモバイル環境での検索速度を考慮して SQLite をキャッシュとして許容するが、基本思想は同じ立場に立つ。

- **人間が読める形式を正とする**：データの「本体」は人間が直接読み書きできるテキスト形式（JSON / YAML / Markdown など）で持つ
- 検索・クエリのために SQLite などをキャッシュとして使うことは許容するが、それはあくまで派生物であり、テキスト形式から再構築できなければならない
- 独自バイナリ形式・プロプライエタリな暗号化は使わない
- スキーマはドキュメント化し、エディタやスクリプトからでも直接操作できる状態を目指す
- フィールド定義はコア層のデータモデルが唯一の真実（single source of truth）

### フロントエンドの独立性

- Android アプリはコア層の「一つのフロントエンド」にすぎない
- CLI ツールや別の UI も同じコアを使って独立して作れる
- Android 固有の処理（通知、カレンダー連携など）はフロントエンド層に閉じ込める

### 現時点の実装判断

初期 MVP では単一 app モジュール内にコアロジックを置き、境界が明確になったタイミングで独立モジュールとして切り出す。最初から分離を強制しない。

## 画面構成（想定）

| 画面 | 役割 |
|---|---|
| Inbox | アイデアの一時置き場 |
| コーチング | AI との対話でプロジェクト化 |
| プロジェクト一覧 | プロジェクトの管理 |
| タイムライン | 今日・明日のタスクのスケジュール表示 |
| レビュー | 一日の振り返りと翌日準備 |
| 設定 | ライフプリセット・通知設定など |

---

## 価値観・設計方針

- **着手ファースト**：完了できなくてもいい。始めることが目標
- **摩擦を減らす**：通知→着手、レビューはスワイプで完結
- **AI は補助**：提案はするが、最終決定はユーザー
- **段階的に深める**：最初は雑でいい。コーチングを重ねるほど精度が上がる
- **コアはオープン**：データモデルとロジックを UI から切り離し、CLI や他のツールからも扱えるようにする（TaskWarrior 的思想）
- **データはユーザーのもの**：ユーザーのタスクや思考の記録は、企業のサーバーではなくユーザー自身が管理するデバイスに置く。サービスが終了してもデータは残り、好きなツールで読める状態を目指す（Local-First の思想）。AI 機能など外部 API への依存は最小限にとどめ、依存する場合も明示する
