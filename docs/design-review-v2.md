2026-04-17 作成。design-review.md（v1）の分析結果を踏まえ、ボトムアップ UI の再設計と既存ツールとの差別化分析を行う。

## 0. このドキュメントの目的

前回のレビュー（design-review.md）で以下が判明した:

1. Memo/Project/Step/DailyLog の4エンティティ構造は **正しい**
2. しかし実装が **「タスク完了」中心** になり、Todoist と同じ力学に陥った
3. Step を「消化するタスク」として扱ったのが根本原因

本ドキュメントでは:
- **そもそもこのアプリを作る必要があるか**（既存ツールで十分か）を正直に評価
- **作る価値がある場合、TaskChute のボトムアップ思考をどう取り込むか** を具体的に設計
- 前回の設計をベースに **最小限の修正で方向転換** する方法を示す

## 1. 既存ツールで十分か — 正直な評価

### 1.1 ユーザーのコアニーズ（7 項目）

| # | ニーズ | 説明 |
|---|--------|------|
| N1 | 10秒キャプチャ | ふわっとしたアイデアを即座にメモ |
| N2 | アイデアの安全な居場所 | タスク化のプレッシャーなく寝かせておける |
| N3 | 段階的な整理 | 気が向いたときにプロジェクトに紐付け |
| N4 | フォーカス機構 | 2-3個に絞って取り組む |
| N5 | 活動の記録（完了ではなく） | 「今日少し進めた」を低負荷で記録 |
| N6 | 進捗の蓄積が見える | やってきたことが積み上がっている実感 |
| N7 | AI によるソフトコーチング | 整理・フォーカス・次のアクションの提案 |

### 1.2 既存ツール比較

| ツール | N1 | N2 | N3 | N4 | N5 | N6 | N7 | 総合 |
|--------|----|----|----|----|----|----|----|----|
| **Todoist** | ○ | × | △ | △ | × | × | △ | 弱い |
| **Things 3** | ○ | △ | ○ | △ | × | △ | × | 弱い |
| **Amazing Marvin** | ○ | ○ | ○ | ○ | △ | △ | × | **惜しい** |
| **Obsidian + Daily Notes** | ○ | ○ | △ | × | ○ | △ | × | 惜しい |
| **Logseq** | ○ | ○ | △ | × | ○ | △ | × | 惜しい |
| **TaskChute Cloud** | △ | × | × | × | ◎ | ◎ | × | 部分的 |
| **Google Keep** | ◎ | ○ | × | × | × | × | × | キャプチャのみ |

### 1.3 各ツールの詳細評価

#### Todoist — 「与えられたタスクの管理」には最適

- アイデアを入れた瞬間に「タスク」になる。寝かせておけない
- 「いつかやる」ラベルはあるが、構造的に「消化するもの」として扱われる
- 期限・優先度が中心。「ふわっとしたアイデアを育てる」設計ではない
- **結論: N1, N2, N5 が根本的に合わない。ユーザーが既に離脱した理由と一致**

#### Things 3 — 「Someday」は近いが活動記録がない

- Someday リストはアイデアの居場所として機能する（N2 △）
- Areas + Projects の構造は整理に使える
- しかし「今日何をしたか」の記録機構がない（N5 ×）
- AI 機能なし
- **結論: 整理は良いが、ボトムアップの「やったこと記録」がない**

#### Amazing Marvin — 最も近い競合

- **Backburner** = N2（アイデアの安全な居場所）
- **Orbit** = N4（フォーカス機構）
- **Task Jar** = ランダム選択（N7 の一部）
- カスタマイズ性が極めて高い

**しかし:**
- コアは依然として **タスク完了モデル** 。活動の記録（N5）は弱い
- 設定項目が多すぎる。「サクッと使う」のとは対極
- モバイル体験がデスクトップより劣る
- AI コーチング機能はない
- 月額$12 / 買い切り$300
- **結論: 機能は網羅的だが「軽さ」と「ボトムアップ」が欠けている**

#### Obsidian / Logseq + Daily Notes — 理論上は可能

- Daily Notes で活動記録（N5 ○）
- Backlinks でアイデア→プロジェクトの関連付け
- 自由度が高い

**しかし:**
- **自分でシステムを構築する必要がある** （テンプレート、クエリ、プラグイン）
- 構造化されたフォーカス機構がない（N4 ×）
- モバイル体験が弱い（特に Logseq）
- 継続にはかなりの規律が必要
- **結論: PKM ツールとしては優秀だが「アプリが導いてくれる」体験ではない**

#### TaskChute Cloud — ボトムアップの本家

- 活動記録（N5 ◎）と進捗の蓄積（N6 ◎）は最強
- 「やったことを記録する」が主操作 — これは正しい

**しかし:**
- **すべての行動を記録する前提** が重い（ユーザーが離脱した理由）
- 時間見積もり・実績管理が負荷
- アイデアの居場所（N2）がない — 「何をやるか決まってから」のツール
- 「やりたいことを探す」フェーズには使えない
- **結論: 記録思想は正しいが、アイデア段階からアクション段階への橋渡しがない**

### 1.4 ギャップ分析 — 何が埋まっていないか

```
          アイデア ─────────→ 整理 ──────→ フォーカス ──→ 活動記録 ──→ 蓄積
            │                  │              │              │            │
Google Keep ◎                  ×              ×              ×            ×
Things 3    ○─────────────────○              △              ×            △
Marvin      ○─────────────────○──────────────○              △            △
TaskChute   ×                  ×              ×              ◎────────────◎
Obsidian    ○─────────────────△              ×              ○            △
```

**どのツールも「アイデア → 整理 → フォーカス → 活動記録 → 蓄積」の全フローを一貫してカバーしていない。**

特に:
- **「アイデアの安全な居場所」と「活動記録」を両立するツールがない**
- Amazing Marvin が最も近いが、活動記録が弱く、設定が重い
- TaskChute は記録が強いがアイデア段階がない

### 1.5 ユーザーの実感との照合

ユーザー（開発者自身）の評価:

- **Amazing Marvin**: 機能が多くて使いづらそう → **「軽さ」が決定的に欠けている**
- **TaskChute Cloud**: 思想はいいがアイデアが溜めにくく、毎回の記録が重い → **N2（安全な居場所）と負荷の問題**
- **既存ツールの組み合わせ**: できなくはないが、フローを一本にまとめたものがない → **統合の価値**

この実感はセクション 1.4 のギャップ分析と完全に一致する。

### 1.6 結論: 作る価値はあるか

**Yes。**

理由:
1. **フロー全体をカバーするツールが存在しない** — 既存ツールの組み合わせでは可能だが、ツール間の移動自体が摩擦
2. **Amazing Marvin は最も近いが「重い」** — 機能の多さ = 設定と学習の負荷
3. **TaskChute は「アイデア段階」がない** — 「何をやるか」が決まってからのツール
4. **Obsidian は自分でシステムを作る必要がある** — 導線がない自由度は高負荷と同義

**このアプリのポジション:**
```
TaskChute の「やったことを記録する」思想
  + Memo の「アイデアの安全な居場所」
  + モバイルファーストの「10秒キャプチャ」
  + AI のソフトコーチング
  + CLI/API による外部連携
  = 「ふわっとしたアイデアから着実な活動へ」を低負荷で橋渡しするツール
```

**既存ツールのどれとも違う点は「アイデア段階から活動記録までを一本のフローで、軽く、モバイルで」という組み合わせ。**
個々の機能では負けるが、このフロー全体をカバーするツールがない。

### 1.7 外部連携の重要性 — CLI/API 窓口

ユーザーの要望: エージェントからの操作がしやすいよう CLI/API 的窓口が欲しい。
TaskChute Cloud 2 や Obsidian がそうなっている。

**これは差別化の重要な柱。**

理由:
1. **AI エージェントとの連携** — Copilot や他のエージェントが直接データを読み書きできる
2. **自動化** — スクリプトで日次レビューの下書き生成、活動ログの集計など
3. **データのポータビリティ** — ロックインを避ける
4. **開発者としての自分自身が使いやすい** — ターミナル志向のユーザーにとってCLIは自然

#### 具体的な API 設計方針

```
# キャプチャ（メモ追加）
idea capture "AIで稼ぐ方法を調べたい"

# 活動記録
idea log "競合A社の料金を調べた" --project "副業リサーチ"

# 今日の活動一覧
idea today

# プロジェクト一覧
idea projects [--focused]

# メモ一覧（未整理）
idea inbox

# ステップ一覧
idea steps --project "副業リサーチ" [--active]

# ステップ完了
idea done "競合3社調査"

# JSON 出力（エージェント向け）
idea today --json
idea projects --json
```

#### 実装アプローチ

| 方式 | メリット | デメリット |
|------|---------|-----------|
| **Room DB を直接読み書きする CLI** | 最もシンプル。同一デバイスで即動く | Android 上でしか動かない |
| **ローカル HTTP サーバー** | 言語非依存。curl で叩ける | バッテリー消費。常駐が必要 |
| **SQLite ファイルの共有** | CLI を別プロセスで動かせる | 排他制御が必要 |
| **エクスポート/インポート（JSON）** | 最も軽量。初期実装向き | リアルタイム性がない |

**推奨: まず JSON エクスポート/インポートから始め、将来的にローカル API へ。**

初期 MVP では:
- `adb shell` 経由で ContentProvider or ファイルベースで JSON 入出力
- CLI ラッパースクリプトを `scripts/` に置く
- これだけでエージェント連携の基本は成立する

将来的には:
- Android の `Foreground Service` + HTTP (localhost) or Unix Socket
- または Kotlin Multiplatform でコアロジックを切り出し、JVM CLI として動かす
  （CLAUDE.md の「コア実装の方針」で既に言及されている方向性と一致）

## 2. TaskChute のボトムアップ思想 — 何を取り込み、何を捨てるか

### 2.1 TaskChute の本質（取り込むもの）

TaskChute の核心は **「計画ではなく記録から始める」** :

| 原則 | TaskChute での実現 | このアプリでの適用 |
|------|-------------------|------------------|
| **記録が先、計画は後** | すべての行動を開始/終了で記録 | 活動を一言で記録（時間不要） |
| **現実ベース** | 実績データから見積もりを改善 | 活動ログから「最近やったこと」を可視化 |
| **未完了に罰なし** | 終わらなかったら翌日に移動 | Step は「やれそうなこと」リスト。終わらなくて当然 |
| **振り返りで改善** | 日次レビューで調整 | 活動ログを見て「今日も少し進んだ」を確認 |

### 2.2 TaskChute の重さ（捨てるもの）

| TaskChute の要素 | なぜ捨てるか | 代替 |
|-----------------|-------------|------|
| 全行動の記録義務 | 負荷が高すぎる | **プロジェクトに関する活動だけ** 記録。家事や雑務は対象外 |
| 開始時刻・終了時刻 | 時間管理がしたいわけではない | **記録なし。** いつやったかは自動タイムスタンプのみ |
| 見積もり vs 実績 | 個人プロジェクトに見積もりは不要 | なし |
| ルーチン管理 | このアプリの対象外 | なし |
| 日次テンプレート | 毎日同じタスクを並べる必要がない | なし |

### 2.3 取り込む「ボトムアップの感覚」

TaskChute で最も価値があるのは **「今日自分は何をしたか」が目に見える** こと。

完了数ではない。**活動の痕跡が残ること** が重要。

```
TaskChute: 9:00-9:30 メール処理 / 9:30-10:15 資料作成 / ...
  → 「今日はこれだけやった」が見える

このアプリ:
  14:30 副業リサーチ: 競合A社のサービスを確認した
  15:00 LP作成: ワイヤーフレーム途中まで書いた
  → 「今日はこの2つのプロジェクトを少し進めた」が見える
```

**TaskChute の「全行動を記録」を「プロジェクト活動だけ記録」に縮小する。**
これが TaskChute の思想を取り込みつつ、負荷を下げる鍵。

## 3. 設計の再構築 — 「活動ダッシュボード」としての Today

### 3.1 今の問題（再確認）

現行の Today 画面:
```
── 副業リサーチ（フォーカス中）
   □ 競合サービスを3つ調べる    [完了]    ← 主操作が「完了」
   □ 収益モデルをメモする       [完了]

── 今日だけのタスク
   □ 牛乳を買う              [完了]

── 今日の記録
   （まだ記録がありません）               ← プレッシャー
```

問題:
1. **「完了」が唯一のアクション** → タスク消化アプリ
2. **ステップが「やるべきこと」として並ぶ** → TODO リスト
3. **「今日の記録」が空だと圧** → 記録義務感
4. **フォーカスプロジェクトが1つしか見えない** → 3つ並行したい

### 3.2 ボトムアップ版 Today — 「活動ダッシュボード」

```
┌─────────────────────────────────┐
│  📝 やったことを記録              │  ← 画面最上部。主操作。
│  ┌─────────────────────────────┐│
│  │ 競合A社の料金体系を調べた    ││  ← テキスト入力
│  └─────────────────────────────┘│
│  [副業リサーチ ▼] [記録]        │  ← プロジェクト選択 + 送信
└─────────────────────────────────┘

── 今日の活動 ──────────────────────
  15:30  副業リサーチ: 競合A社の料金体系を調べた
  14:00  LP作成: ヘッダーのコピーを3案書いた
  ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─
  （活動が増えるほどリストが育つ = 達成感）

── フォーカス中 ────────────────────
  🔵 副業リサーチ（3週目・最終活動: 今日）
     次にやれそう: 競合3社調査 / 収益モデルメモ

  🟢 LP作成（1週目・最終活動: 今日）
     次にやれそう: Figma で清書

  🟡 Kotlin勉強（2週目・最終活動: 3日前）
     次にやれそう: Coroutines の章を読む
```

### 3.3 設計原則の比較

| | 現行（v1 実装） | 提案（v2 ボトムアップ） |
|---|---|---|
| 画面の主役 | ステップ一覧（TODO リスト） | **活動記録フォーム + 今日のログ** |
| 主操作 | 「完了」ボタン | **「記録」ボタン** |
| ステップの役割 | 消化すべきタスク | **次にやれそうなことのヒント** |
| ステップの完了 | Today 画面で行う | **Projects 詳細で行う** |
| フォーカスPJ表示 | 1つだけ | **全部（2-3個）** |
| 空状態 | 「記録がありません」（圧） | **記録フォームが常にある（圧なし）** |
| ログの成長方向 | ステップ完了で自動追加 | **ユーザーが能動的に記録** |

### 3.4 なぜ「記録」が主操作であるべきか

**TaskChute の核心的洞察: 「何をしたか」を記録する行為自体が、次の行動を促す。**

理由:
1. **記録すると「今日も少し進んだ」が可視化される** → 継続のモチベーション
2. **「何を記録しよう？」と考えることが、次にやることを考えるきっかけになる**
3. **空のTODOリストは「やるべきことが山積み」という圧。空の活動ログは「まだ何もしてない」ではなく「これから記録する」**
4. **完了を求めないので、5分の作業でも記録できる** → 着手のハードルが下がる

**「完了」が主操作のアプリ:**
```
開く → TODO を見る → 「うーん、どれも今日中に終わらないな…」 → 閉じる
```

**「記録」が主操作のアプリ:**
```
開く → 何かやる → 「30分だけ調べた」と記録 → 「今日も進んだ」 → 閉じる
```

この差が、**着手ファーストの思想** を体現するかどうかの分岐点。

### 3.5 「次にやれそう」のヒント表示

フォーカスプロジェクトのセクションに active なステップを **ヒントとして** 表示する。

```
🔵 副業リサーチ（3週目）
   次にやれそう: 競合3社調査 / 収益モデルメモ / ターゲット仮決め
```

これは:
- タップしても「完了」にはならない（Today では完了操作なし）
- **「何やろうかな」のとき参考になる** だけ
- ステップがなくても活動記録はできる（ステップ外の作業も OK）
- ステップを追加したければ Projects タブへ

**ステップは「指示」ではなく「アイデアリスト」。** この位置づけが重要。

## 4. 3 タブの再定義

### 4.1 タブ構成（変更なし）

```
Today | Capture | Projects
```

タブ構成自体は変えない。変えるのは **各タブの中身と役割** 。

### 4.2 Today — 「活動ダッシュボード」

**役割: 今日の活動を記録し、フォーカスプロジェクトの状況を俯瞰する**

構成:
1. **活動記録フォーム**（最上部。常に表示）
   - テキスト入力 + プロジェクト選択ドロップダウン + 記録ボタン
   - プロジェクト未選択でも「プロジェクトなし」で記録可能（雑務記録）
2. **今日の活動ログ**（時系列。新しいものが上）
   - タイムスタンプ + プロジェクト名 + what
   - スワイプで削除（誤記録の取り消し）
3. **フォーカス中プロジェクト**（カードで横に並べるか、縦リスト）
   - プロジェクト名 + 経過期間 + 最終活動日
   - active ステップを 2-3 個ヒント表示
   - タップ → Projects 詳細に遷移

**Today から消すもの:**
- ステップの「完了」ボタン
- 「今日だけのタスク」セクション（後述: 用途を再考）
- 「まだ記録がありません」テキスト

### 4.3 Capture — 「アイデアの安全な居場所」

**役割: 思いつきを即座にメモし、気が向いたら整理する**

構成（現行からの変更点）:
1. **入力フォーム**（現行のまま。変更不要）
2. **未整理メモ一覧**（現行のまま）
3. **整理操作の改善:**
   - メモ長押し → 複数選択モード → 一括でプロジェクトに紐付け
   - 紐付けダイアログ内に「+ 新規プロジェクト」ボタン
   - AI 候補は一覧にインライン表示（ダイアログの外）

**Capture は v1 の設計でほぼ正しい。** バッチ操作を追加するだけ。

### 4.4 Projects — 「整理と管理の場所」

**役割: プロジェクトの構造化・ステップ管理・進捗確認**

プロジェクト一覧:
- フォーカス中を上部に強調（現行のまま）
- 最終活動日を表示（追加）
- 放置中プロジェクトの視覚的区別（3日以上活動なし → 薄い色）

プロジェクト詳細:
- 背景メモ（現行のまま）
- **ステップ一覧（ここで完了/凍結操作）**
  - active / done / icebox のセクション分け
  - ステップの追加・並べ替え・完了・凍結
- 関連メモ一覧（現行のまま）
- **活動ログ**（DailyLog からこのプロジェクトのものをフィルタ。追加）
- フォーカス/休止/アーカイブ（現行のまま）

## 5. データモデルの修正

### 5.1 変更点（v1 からの差分）

**Step:**
```
status: PENDING | DONE     →  ACTIVE | DONE | ICEBOX
visibility を削除          →  status に統合（ICEBOX = 旧 icebox visibility）
```

**DailyLog:**
```
stepId: Long?              →  projectId: Long?
（ステップ完了の自動記録    →   ユーザーが能動的に記録）
```

### 5.2 改訂データモデル

```
Memo（アイデア・思いついたこと）
  id: Long
  text: String
  projectId: Long?         // 紐付け先（= 整理済み）
  createdAt: Long

Project（取り組みのまとまり）
  id: Long
  title: String
  background: String?
  status: ACTIVE | PAUSED | ARCHIVED
  focusedAt: Long?         // != null ならフォーカス中
  createdAt: Long

Step（やれそうなこと・やりたいこと）
  id: Long
  projectId: Long
  title: String
  sortOrder: Int
  status: ACTIVE | DONE | ICEBOX
  doneAt: Long?
  createdAt: Long

DailyLog（活動の記録）
  id: Long
  date: String             // "2026-04-17"
  projectId: Long?         // null = プロジェクト外の活動
  what: String             // 「競合A社の料金体系を調べた」
  createdAt: Long          // タイムスタンプ（時刻表示用）
```

### 5.3 「今日だけのタスク」について

v1 には `projectId: null` の Step（ad-hoc タスク）があった。

**提案: 廃止する。**

理由:
- ad-hoc タスク（「牛乳を買う」）は Todoist の領域
- このアプリに混ぜると **「TODO アプリ」感が戻る**
- 代わりに DailyLog の `projectId: null` 記録で「プロジェクト外の活動」を記録できる
- 本当にタスク管理が必要なら Todoist を使えばいい

**このアプリは「個人プロジェクトの活動記録」に絞る。雑務管理は対象外。**

## 6. ボトムアップフローの全体像

### 6.1 ユーザーの1日

```
【思いついたとき】（5-10秒）
  Capture → 「AIで稼ぐ方法を調べたい」→ 追加
  → メモとして安全に保存。タスク化されない。

【何かに取り組んだとき】（10-20秒）
  Today → 「競合A社の料金を調べた」→ 副業リサーチ → 記録
  → 活動ログに追加。ステップの完了は不要。

【気が向いたとき】（数分）
  Capture → 溜まったメモを眺める → プロジェクトに紐付け
  Projects → ステップを追加・整理

【たまに】（週1程度）
  Projects → フォーカスを見直す
  Projects → icebox を棚卸し
  Today → 活動ログを振り返る（「今週けっこう進んだな」）
```

### 6.2 TaskChute との対応

```
TaskChute:        記録 → 振り返り → 改善 → 記録 → ...
このアプリ:       キャプチャ → 記録 → 振り返り → 整理 → 記録 → ...
                  ↑                              ↑
             アイデア段階を追加          整理を明示的に分離
```

**TaskChute の「記録 → 振り返り」ループを維持しつつ、前段に「キャプチャ → 整理」を追加。**
これが TaskChute にはない「アイデアから行動への橋渡し」を実現する。

### 6.3 フロー図

```
┌──────────┐     ┌──────────┐     ┌──────────┐
│ Capture  │     │ Projects │     │  Today   │
│          │     │          │     │          │
│ メモ投入  │────→│ 紐付け    │     │ 記録     │
│ (発散)   │     │ ステップ化 │────→│ (蓄積)   │
│          │     │ フォーカス  │     │          │
└──────────┘     └──────────┘     └──────────┘
                       ↑                │
                       └────────────────┘
                      活動ログから進捗を確認
                      → フォーカス・ステップ調整
```

**時間軸:**
```
アイデア段階（Capture）→ 整理段階（Projects）→ 実行段階（Today で記録）
     発散                    収束                  蓄積
```

## 7. AI 機能の位置づけ（ボトムアップ版）

### 7.1 AI の役割変更

v1 では AI が「次にやるステップを推奨」していた。
v2 では **AI は「整理と気づきのアシスタント」** に徹する。

| 優先度 | タイミング | v1 | v2（ボトムアップ版） |
|--------|-----------|----|----|
| 高 | Capture 時 | メモ→PJ 関連候補 | **同じ（変更なし）** |
| 中 | Today 表示時 | ステップ優先順提案 | **「最近○○を進めてないですね」** |
| 中 | 活動記録時 | — | **記録内容からステップ完了を提案**（新規） |
| 低 | Projects 一覧 | 放置PJ の休止提案 | **同じ（変更なし）** |

### 7.2 新しい AI 機能: 記録からの提案

活動を記録したとき:
```
ユーザー: 「競合A, B, C社の料金を一通り調べた」（副業リサーチ）
AI: 「『競合3社調査』ステップ、完了にしますか？」 [はい / いいえ]
```

**活動記録 → AI がステップ完了を検知 → 確認だけ求める。**

これにより:
- ユーザーは「記録」だけすればいい
- ステップの完了は AI が気づいて提案
- 完了操作を能動的にやる必要がない
- **ボトムアップ: 記録が先、整理は後**

### 7.3 AI なしの場合

すべて手動で動く:
- Capture の紐付けは手動選択
- ステップ完了は Projects 画面で手動
- フォーカス提案なし（自分で選ぶ）
- 放置警告なし（自分で気づく）

**AI なしでも「活動記録 → 蓄積 → 振り返り」のコアループは機能する。**

## 10. リスクと注意点

### 10.1 「記録が面倒」リスク

TaskChute の最大の離脱理由は記録の負荷。このアプリでも:
- 記録が1日0回でも問題ないこと
- 記録しなくてもアプリが機能すること（Capture や Projects は独立）
- 「記録がない日」に罰や警告を出さないこと

**記録は「したくなったらする」もの。義務にした瞬間に TaskChute と同じ轍を踏む。**

### 10.2 「ステップが形骸化」リスク

ステップが「ヒント表示」だけになると、誰も更新しなくなる可能性:
- 対策: AI が活動記録からステップ完了を提案（セクション 7.2）
- 対策: Projects 詳細で「最終更新: 30日前」を表示
- 対策: ステップが0件でも活動記録はできる（ステップ管理は任意）

### 10.3 「Amazing Marvin でよくない？」リスク

正直な懸念。差別化のために必要なこと:
1. **起動から記録まで10秒** （Marvin は設定が多い）
2. **活動記録がコア体験** （Marvin はタスク完了がコア）
3. **AI コーチング** （Marvin にはない）
4. **CLI/API 窓口** （Marvin にはない。エージェント連携不可）
5. **無料・オープンソース** （Marvin は有料）

## 11. 結論

### 11.1 作る価値

**Yes。「アイデア → 整理 → フォーカス → 活動記録 → 蓄積」を一本のフローでカバーするツールは存在しない。**

既存ツールの組み合わせ（Obsidian + TaskChute + Todoist 等）でフローの各部分はカバーできるが、ツール間の移動が摩擦になり、結局どれかを使わなくなる。一本化する価値がある。

加えて CLI/API 窓口を持つことで:
- エージェントからの操作が可能（TaskChute Cloud 2 や Obsidian と同等）
- 開発者自身のターミナル志向ワークフローに合致
- データのポータビリティとカスタマイズ性を確保

### 11.2 最も重要な設計変更

**Today 画面の主操作を「ステップ完了」から「活動記録」に変える。**

これ1つで:
- TaskChute のボトムアップ思想が入る
- Todoist との差別化が明確になる
- 「着手ファースト」の思想が UI に体現される
- 5分の作業でも記録できる → 着手のハードルが下がる

### 11.3 このアプリのアイデンティティ

```
「何をすべきか」を管理するアプリではない。
「何をしたか」を記録するアプリ。

タスクを消化するのではなく、活動を積み上げる。
完了を求めるのではなく、着手を祝う。
計画から始めるのではなく、記録から始める。
```

## 12. 次のエージェント（Claude Sonnet 4.6）へのステップ指示

### 12.1 現状の問題の正体

開発者は **プロトタイプを複数回作り直したが、どれもしっくり来ていない** 。しかし「UI が悪いのか、試し方が悪いのか分からない」という状態。

**これは設計の問題ではなく、検証プロセスの問題である可能性が高い。**

根拠:
1. どのプロトタイプも **2週間以上連続して実使用されていない**
2. 「しっくり来ない」の具体的な内容（どの画面のどの操作でいつ摩擦を感じたか）が記録されていない
3. 設計変更のたびにゼロから作り直しており、**前の設計で何が良くて何が悪かったかが計測されていない**
4. 「良さそう」「悪そう」という直感で判断しているため、**バイアスがかかっている可能性がある**（新しいものは良く見え、使い慣れたものは飽きる）

つまり「UI が悪い」ではなく「UI を判断するためのデータがない」が真の問題。

### 12.2 まずやるべきこと（絶対に先にやる）

**新しい実装を始める前に、現状のプロトタイプ（v1 実装: Memo/Project/Step/DailyLog）を 3日間 集中的に dogfooding する。**

これをやらずに新しい設計に進むと、また同じ「しっくり来ない」を繰り返す。

#### なぜ3日で足りるか

2週間の連続使用は理想だが、開発者がしんどくて継続できない可能性が高い。
**本当に必要なのは「期間の長さ」ではなく「観察の質」。**

- 3日でも摩擦点は十分出る — 1日目のキャプチャ衝動、2日目の整理欲求、3日目の記録継続性
- 観察の質を上げるために **事前に検証したい問いを決めておく** 方が重要
- 3日で判断がつかなければ +3日延長する（最大2週間まで）

#### dogfooding のルール

1. **最低3日連続で使う**（スキップした日があれば 1日追加）
2. **事前に検証したい問いを3〜5個決めておく** （下記参照）
3. **設計を変更しない** （バグ修正のみ。UI 変更・機能追加は禁止）
4. **摩擦点を即座に記録する**:
   - アプリ内に「フィードバックメモ」プロジェクトを作り、摩擦の瞬間に Capture で投入
   - または別の場所に日付＋時刻付きでメモ
5. **数値も取る**（使用ログ機能で自動記録）:
   - キャプチャ数・活動記録数・タブ別開いた回数・使わなかった日

#### 事前に決める「検証したい問い」の例

この問いがないと、dogfooding は「ただ使うだけ」になり気づきが得られない。
3日の短期勝負では以下のように具体的に絞る:

- Q1: **キャプチャは1日に何回発生するか？** 0回なら捕捉体験に問題がある
- Q2: **Today を自発的に開いたか？** 開かないなら画面の動機設計が弱い
- Q3: **ステップの「完了」を押したくなる場面があったか？** ないなら Step モデルの前提が間違い
- Q4: **活動を記録したいのに記録できなかった場面があったか？** あれば UI のボトルネック
- Q5: **アプリを開くよりメモ帳・Obsidian に書いた方が早いと感じたか？** 感じたなら根本的に負け

**この問いのどれに対しても明確な答えが出れば、3日で十分。**

#### ログのためのコード追加（最小限の計測機能）

開発者に以下を追加実装させること:

```kotlin
// UsageLogEntity（新規）
  id: Long
  timestamp: Long
  event: String       // "tab_opened:today" / "memo_captured" / "step_done" / "log_recorded" / ...
  metadata: String?   // 必要なら JSON
```

各画面・各操作で `UsageLogRepository.record(event)` を呼ぶだけ。
3日後、`SELECT event, COUNT(*) FROM usage_log GROUP BY event` で傾向が見える。

**これなしに設計議論を続けるのは時間の無駄。**

### 12.3 3日後の判断フロー

dogfooding 後、以下の判断を行う:

#### ケース A: ちゃんと使えている（キャプチャ > 5件、活動記録 > 2件、日数スキップなし）

- 摩擦点が局所的（「この操作だけ面倒」レベル）

→ **現在の設計は概ね正しい。局所的な改善を加えるだけでよい。**
→ Today を「活動ダッシュボード化」する v2 の変更は実施する価値あり
→ CLI/API 実装にも進む

#### ケース B: 使えていないが原因が明確（特定操作で詰まる / タブに入る動機がない）

- 例: 「Capture のダイアログが重い」「Today に入る動機がない」

→ **該当部分だけをピンポイント修正する。**
→ 全体の作り直しは不要
→ 修正後に Before/After で +3日ずつ測定

#### ケース C: 根本的に使えていない（アプリを開くこと自体が習慣化しない）

- そもそもアプリを開く回数が極端に少ない
- キャプチャすら発生しない
- 「スマホで文字を打つこと自体が摩擦」
- 「Obsidian に書いた方が早い」と感じる場面が多い

→ **アプリ設計の問題ではなく、前提が間違っている可能性。**
→ 以下を検討:
  - ウィジェット・通知経由の投入
  - 音声入力
  - PC/CLI からの投入（CLI/API 窓口の前倒し実装）
  - そもそも Obsidian + Daily Note で運用する方が合っている可能性

#### ケース D: 3日では判断できない（データが中途半端・摩擦が曖昧）

→ **+3日延長する**（合計6日）
→ それでも判断できなければ +1週間延長
→ 最終的に2週間経っても結論が出なければ、設計以前の問題（生活リズム、モチベーション、アプリカテゴリそのもの）を疑う

### 12.4 dogfooding と並行して検証すべき対照実験

**「このアプリが必要」を検証するために、以下の軽い対照実験を並行して行う:**

1. **3日間の前半2日**: プロトタイプのみを使う
2. **3日目**: Obsidian（または紙のノート）で同じことを並行してやる
   - Daily Note にメモ + 「今日やったこと」
3. **比較**:
   - どちらに先に手が伸びたか
   - どちらでアイデアが溜まったか
   - アプリを開くのが億劫だった瞬間があったか

3日では完全な比較はできないが、**「アプリを開くより Obsidian に書く方が早い」と感じる瞬間があれば黄色信号**。
頻発するならケース C と判定。

### 12.5 Sonnet 4.6 への具体的な依頼事項

次のエージェントには **実装を進めさせる前に以下を遂行させる** こと:

#### タスク 1: 使用ログの実装（最優先）

```
1. UsageLogEntity / UsageLogDao / UsageLogRepository を追加
2. AppDatabase version を 7 に上げる（DailyLog の変更と同時でもよい）
3. 以下の箇所で record() を呼ぶ:
   - 各タブを開いたとき: "tab_opened:{today|capture|projects}"
   - Memo を追加したとき: "memo_captured"
   - Memo をプロジェクトに紐付けたとき: "memo_linked"
   - Step を追加したとき: "step_added"
   - Step を完了したとき: "step_done"
   - DailyLog を記録したとき: "log_recorded"
   - Project をフォーカスしたとき: "project_focused"
4. 簡易レポート表示（開発者用の隠し画面でよい）:
   「過去7日間の統計」画面で各イベントのカウントを表示
5. CSV エクスポート機能（開発者が解析できるように）
```

#### タスク 2: 開発者に dogfooding 依頼

- 実装完了後、開発者に以下を明示的に伝える:
  > 「次の設計変更を行う前に、現状のアプリを3日間連続で使用してください。事前に検証したい問い（Q1〜Q5）を明確にし、変更・機能追加はせず、使用ログを収集してください。3日後のログデータをもとに次のステップを判断します。判断がつかなければ +3日 延長します。」

- 使用ログが不足している場合、設計判断のためのデータがないことを明確に伝える

#### タスク 3: dogfooding 期間の作業（任意・軽微な改善のみ）

3日の dogfooding 中にできること:
- バグ修正（クラッシュ・データロス等の重大なもののみ）
- CLI/API 窓口の初期実装（アプリ本体の UX には影響しない）
  - JSON エクスポート機能
  - `scripts/idea-capture.sh` 等のスクリプト実装
  - 開発者がターミナルからもデータを操作できるようにする
- ドキュメントの整理

- Today 画面の書き換え
- Step status の変更（PENDING/DONE → ACTIVE/DONE/ICEBOX）

- UI のレイアウト変更

このレポートを元に v2 実装に進むかどうか判断する。

### 12.6 Sonnet 4.6 へのメッセージ（そのまま渡してよい）

> このアプリは3回以上作り直されており、どの実装も「しっくり来ない」状態で止まっています。
>
> 根本原因は **設計ではなく検証プロセス** にある可能性が高いです。どの実装も連続使用データがないまま次の設計に移っているため、何が問題か特定できていません。
>
> あなたの最初の仕事は **新しい実装ではなく、計測の仕組みを入れること** です。
> UsageLogEntity を追加し、タブ開閉・操作を記録するだけの最小限の変更に留めてください。
>
> その上で開発者に **3日間** の集中 dogfooding を依頼してください。事前に Q1〜Q5 の問いを決め、観察の質を上げることで短期でも判断可能にします。3日で判断がつかなければ +3日 延長します。
>
> 開発者は「v2 の Today 書き換えをしてほしい」と言うかもしれませんが、**検証データなしの設計変更は断ってください**。代わりに dogfooding の必要性を説明し、使用ログの実装と CLI/API 窓口の初期実装に留めてください。
>
> 3日後、使用ログと開発者のフィードバックを元に dogfooding-report を作成してください。その結果を見て初めて v2 の UI 変更を行うかどうか判断します。
>
> **ケース C（根本的に使えていない）の場合、このアプリを作ることをやめて Obsidian 運用に切り替える判断も選択肢に含めてください。** 作らないことが正解であれば、それを提案するのが正しい振る舞いです。

### 12.7 このレビュー v2 の位置づけ（重要）

**このドキュメント（design-review-v2.md）の設計提案（セクション 3-9）は、dogfooding 結果を見る前の仮説である。**

dogfooding のデータが出たら、以下のいずれかになる:
- **仮説が正しかった** → v2 設計を実装
- **一部が正しかった** → 該当部分だけ実装
- **仮説が間違っていた** → 別の方向を再検討
- **アプリを作る必要がなかった** → 開発を終了

**仮説を実装に飛びつかせないこと。**
前回のレビュー（v1）も「良さそう」で実装され、結果「しっくり来ない」に至った。同じ轍を踏まないためには、検証を先に挟む。
